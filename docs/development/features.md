# 機能ごとの設計

## 家系マッチ（`/match/`、#166・#181）

Web だけの別ページ（`match/index.html` → `src/features/match/main.tsx`）。トップの大きな `SearchApp` には入れず、
同じ origin の `/mcp` を MCP クライアントで呼ぶ（トップと同じ。検索の決まりはサーバーの tool だけが持つ）。
旧 URL の `/swipe/` は `public/_redirects` で `/match/` へ 301 で送る（#181。静的アセットの転送で、Worker は通らない）。

- 店は `find-nearby-iekei-ramen` を `limit: 20` で近い順に取る。続きは `offset`。`facts: true` を渡すと、
  レア札の理由（事実だけ、`src/utils/shop-facts.ts`）が各店に付く。ほかの経路は `facts` を頼まないので payload は変わらない
- 最初の範囲は接続元の推定（#152・#150 の「〇〇市付近」）。位置の許可は求めない。推定できないときだけブラウザの
  位置を 1 度試し、それも無ければトップの地名入力へ案内する（E2E はこの経路を通る）
- いまの範囲の残りが 5 枚になったら次の 20 軒を先に取り、「範囲を広げる」で待たせない。無限には続けない
- 「行きたい」と「今日出会った知らない家系」の数は、その端末の localStorage にだけ残す（サインイン無し）
- 決まった店のシェアは文字だけ（X・Threads の投稿画面へのリンク）。画像つきのカードは #46 と合流させる
- MCP（会話の中）には出していない（#166 の見本の後に決める）
- **最初の表示を JavaScript に待たせない**（#203）。`match/index.html` の `#root` に上の行（ロゴと見出し）の骨組みを入れてあり、
  React が描くと丸ごと入れ替わる（ずれにならない）。上の行の見た目を変えたら骨組みも直す（E2E が位置のずれを見る）
- 店を探す接続（`src/lib/feed.ts`）は、最初に店を頼んだときに始める。家系カメラは撮るボタンに触れたら始める（`warm`）。
  開いた直後に接続の部品（約 88KB）を読むと、最初の表示と回線を取り合っていた

## 家系タイプ診断（`/shindan/`、#167）

Web だけの別ページ（`shindan/index.html` → `src/features/shindan/main.tsx`）。問い・タイプ・注文の呪文は `src/utils/shindan.ts` が持つ。

- 回答は送らず、残さない（画面の中だけで結果を出す。サーバーも呼ばない）
- シェアの URL はタイプごとの紙 `/shindan/<タイプ>/`。中身は診断と同じページで、開くと 1 問目から始まる。
  `scripts/build/build-seo.mjs` がビルドの後に、OGP の題と画像だけを差し替えて作る
- シェア画像（`public/og/shindan-<タイプ>.png`、1200×630）は `node scripts/assets/shindan-og.mjs` で作ってコミットする。
  タイプ名か文言を変えたときだけ回す
- 投稿画面の URL は `src/utils/share.ts`（#46 と共有。X を左、Threads を右に並べる）

## 家系カメラ（`/camera/`、#190）

Web だけの別ページ（`camera/index.html` → `src/features/camera/main.tsx`）。投稿文のひな形は `src/features/camera/utils/camera-post.ts`、
写真の仕上げは `src/features/camera/lib/photo.ts`。

- 写真はサーバーに送らず、保存しない。加工は canvas で端末の中だけ。canvas から書き出すと EXIF（位置情報）は付かない
  （`e2e/camera.spec.ts` で、位置情報入りの写真から書き出したものに EXIF が無いこと・送った通信が小さいことを確かめる）
- 店の候補は家系マッチと同じ `createFeed`（接続元の推定 → ブラウザの位置 → 地名）。店の中で使うので「いまいる場所で探し直す」がある
- 投稿は Web Share API（写真と文）。渡せない端末（PC）では写真を保存し、文をコピーして投稿画面を開く
- 検索エンジンに載せる（#242。`/match/`・`/shindan/` と同じく sitemap に入れる）

## 迷ったら（3 軒に絞ってモデルに推させる）

**画面に出る名前は「迷ったら」。コード上の識別子は `decide` のまま**
（tool 名 `decide-iekei-ramen`、`DecidePanel`、`mode: "decide"`）。
文言だけ直したいときに、型や tool 名まで巻き込まないようにしてある。

券売機の「近くで」は、基準地点が無ければブラウザの位置を 1 度試し、取れなければ
`decide-iekei-ramen` に `near: true` を渡す（#147）。サーバーは find-nearby と同じ順
（ホストの位置 → 接続元の推定）で現在地を探し、どれも取れなければ全国から並べずに
`decide.needsOrigin` を立てて 0 軒で返す。現在地の画面（find-nearby）へは回さない。
そこの検索は味の傾向を受け取らず、選んだ条件と 3 軒が消えるため。

ホストの位置と接続元の推定は、名前（city / region）がローマ字で来る（「Saitama Saitama」）。
サーバーは推定座標にいちばん近い収録店の市区町村（20km 以内）か都道府県（80km 以内）を借りて
「横浜市付近」と呼び、それより遠ければ「現在地付近」にする（`server/utils/place-label.ts`、#150）。
外部の逆ジオコーディングは呼ばない。端末の位置（「現在地」）と地名は名前を変えない。

564 件の一覧は選択肢地獄で、人は理由の無い長い一覧からは決められない。
3 軒まで落として、決める仕事はモデルに渡すのが `decide-iekei-ramen`。

- 候補の選び方は [src/utils/shortlist.ts](../../src/utils/shortlist.ts) に隔離してある。
  **勝手な「おすすめ順」を作らないこと。** このデータには評価も混雑も口コミも
  無いので、質の順位は付けられない。並べていいのは実際に持っている情報だけ
  （家系判定の段階・距離・営業時間の有無）。
- **乱数を使わない。**「次の 3 軒を見る」は次の 3 軒であって、シャッフルではない。
  決定的なので、同じ条件なら毎回同じ並びになりテストできる。
- なぜこの 3 軒なのかは `describeBasis` が 1 文にする。**UI とモデルに同じ文を見せる。**
  別々に書くと、画面の説明と会話の説明がずれる。
- サーバーが返す text はモデルへの依頼文を兼ねている。使っていい材料を明示して
  縛らないと、モデルが「濃厚で人気」などと知識から補ってしまう。
- UI から呼ぶと `ontoolresult` が来ない＝依頼文がモデルに届かない。
  「この 3 軒から選ぶ」は `sendMessage` で候補ごと送り直す。

## まわる店（2〜3 軒の順路）

**画面に出る名前は「まわる店」。コード上の識別子は `route` / `stops`。**
「はしご」とは呼ばない——ラーメン好きの内輪語で、知らない人には梯子に読める。

決めたあと、ユーザーは必ずアプリを出て地図アプリを開く。そこが手作業のままだと
体験が途切れるので、順番・距離・地図アプリへの受け渡しまでを UI で完結させる。

- 順番の計算は [src/utils/route.ts](../../src/utils/route.ts) に隔離してある。
  上限 3 軒なので全順列（最大 6 通り）の総当たりで最短を選ぶ。**貪欲法は使わない**
  （1 軒目を間違えると戻る形になる）。同点は積んだ順を残すので、結果は決定的。
- **距離は直線距離。徒歩◯分に換算しない。** 経路探索のデータを持っていないので、
  時間を出すと「間に合うか」の判断材料に化ける。画面にも直線距離だと書く。
- 積んだ店は外側の `SearchApp` が持ち、**検索し直しても消さない**。別の条件で
  見つけた店を足していくものなので、payload ごとに消すと組み立てられない。
  選択（1 軒・モデルに渡す）とは寿命も役割も別。
- **出発点も一緒に持つ。今の payload から取らない。** 店だけ残して出発点を
  payload 由来にすると、基準地点を持たないモード（検索フォーム・地図）へ移った
  瞬間に出発点が消え、順路が並べ替わる（実測: 「壱八家 → ありがた家・合計 918m」
  がタブを押しただけで「ありがた家 → 壱八家・合計 646m」になった）。最初の
  1 軒を入れたときの基準地点を、空になるまで持ち続ける。
- **渡せる先は Google マップだけ。Apple マップは載せない。** Google は
  `waypoints`（パイプ区切り、モバイルで 3 件まで）が公式にあり、3 軒の順路が
  そのまま開く（実測: 出発点 + 経由地 2 + 目的地で徒歩 28 分 / 1.9km）。
  **Apple の URL には経由地にあたるパラメータが無い。** `daddr` は目的地 1 つ
  だけで、Google 由来の `daddr=A+to:B` は 1 つの住所文字列として扱われ、解決
  できずに 1 軒目すら開かない（実測: `destination=35.5...%20to%3A35.4...`）。
  1 軒目までなら渡せるが、それでは「まわる店」の用を成さないので**ボタンごと
  置いていない**。Apple 側が経由地を受け取れるようになるまで戻さないこと。
- **渡すのは座標で、店名は渡さない。** 地図アプリ側は受け取った座標を自前の
  POI に寄せて表示するので、**同じ場所なのに別の店名で出ることがある**
  （実測: 壱八家の座標が「築地食堂源ちゃん 横浜スカイビル店」と表示された。
  同じ建物の別テナント）。店名で渡すと曖昧で別の店へ案内しかねないので、
  位置が確実な座標を優先する。
- 地図に線を引く節は、**「選んだ店へ寄せる」より後に置くこと。** 同じ更新で
  両方走ると後の地図移動が勝ち、前に置くと順路が画面の外へ出る。

## 訪問スタンプ（サインインが要る唯一の機能）

**匿名の検索は止めない。** `/mcp` は誰でも叩け、記録の 3 tool（`MEMBER_TOOLS`）
だけが、トークンの無い呼び出しに 401 を返す。ホストはこの 401 を見て
「アクセス権を更新」を出す（ChatGPT で実測）。

- ディレクトリ向けの認証宣言は各toolの `securitySchemes` と、その互換用の
  `_meta.securitySchemes`。[OpenAIの宣言形式](https://developers.openai.com/plugins/reference#_meta-fields-on-tool-descriptor)に合わせる。
  現在のMCP SDKは登録時に独自キーを落とすため、SDKの `tools/list` 応答にトップレベルの宣言を追加する。
  匿名検索の4 toolは `noauth` と任意の `oauth2` を両方宣言し、サインイン後の訪問印も返せることを伝える。
  地名検索は `noauth` のみ、`MEMBER_TOOLS` は `oauth2` のみ。結合テストで一覧の両方の宣言を検証する。
  スタンプは `visited=false` で印を削除するので、全削除と同じく `destructiveHint: true`。
- 身元は Google に委ねる（`openid` だけ。**審査不要の範囲**）。受け取った `sub` は
  専用の鍵で HMAC してから保存し、**生の sub は持たない**。この鍵
  （`VISITOR_ID_PEPPER`）は二度と変えられない——変えると全員の記録が迷子になる
- 記録は D1、認可の状態は KV。認可サーバーは `@cloudflare/workers-oauth-provider` の
  `OAuthAuthorizationServer`。**`OAuthProvider` は使えない**（apiRoute の未認証を
  ハンドラ手前で 401 にするので、匿名が通らなくなる）
- Googleへ進む前に、クライアント名・戻り先ホスト・訪問記録の閲覧/変更/全削除の
  権限を示し、毎回明示的な許可を求める。Googleの本人確認とは別の判断。
  `beginConsent` / `approveConsent` / `denyConsent` に検証済み要求とCookieの管理を
  任せる。フォームのclient_idやredirect_uriは使わない。許可画面はiframeを拒否する。
  許可画面のCSPの `form-action` は自身・Googleの認証先・検証済みの戻り先を許可する。
  ChromiumはフォームPOST後のリダイレクトも検査するため、`'self'` だけでは
  同意Cookieを消費した後にGoogleへの転送が遮断される。
  `e2e/oauth-redirect.spec.ts` が許可と拒否の実フォーム操作を検証する。
- **`/.well-known/oauth-protected-resource` は自分で返す**（[oauth.ts](../../server/lib/oauth.ts)）。
  ライブラリは認可サーバー側の文書しか出さず、任せると 401 の指す先が 404 になる
- ライブラリは `cloudflare:workers` を取り込むので**動的 import**。KV の無い環境
  （Node の手元サーバー）では読み込ませず 501 を返す。読み込むとプロセスごと落ちる
  （ESM ローダの失敗は try/catch で拾えない）
- **UI から記録の tool を呼べるのはサインイン済みのときだけ。** 匿名で呼んでも
  401 を受けるだけで、ホストはサインインの画面を出さない（出すのはモデル発の
  呼び出しに対してだけ）。匿名の「行った」は `sendMessage` でモデルに頼み直す
  （文面は [shop-brief.ts](../../src/features/search/utils/shop-brief.ts)）
- **サインインしているかは `payload.visited` の有無で判る。** 匿名ではこの欄ごと
  落としてあるので、「1 軒も行っていない人」（空配列）と混ざらない
- **スタンプの結果で画面を差し替えない。** `includeShops` は既定で `true`。
  モデルや既存ホストには従来どおり `mode: "visited"` の店舗一覧を返す。
  検索・地図などのUIは `false` を渡し、訪問IDと制覇率の全体snapshot
  （`visited` / `progress`）だけを受け取る。`readVisitResult` / `applyVisits` が
  記録だけを反映し、検索結果と選択を維持する。「行った店」画面は一覧が必要なので
  `true` を渡す。どちらも書き込み後の1回の読み取りから組み、UIの操作は直列に送る
- 応答サイズの再計測は `node --import tsx scripts/dev/benchmark-stamps.mjs`。
  実データの訪問0件・100件・全件で、MCP tool結果のJSON全体をUTF-8で比較する。
  HTTP/SSEの付加分と圧縮後の転送量は含めない。記録はメモリだけで、本番のD1へは書かない
- **保存するもの・外部に送る先を変えたら、規約の下書き（[docs/legal/](../legal/README.md)）も直す。**
  プライバシーポリシーは実際の持ち方と 1 対 1 で書いてあり、ディレクトリの審査で照らし合わされる（#47）
- 制覇率の計算は [src/utils/progress.ts](../../src/utils/progress.ts)。**順位も称号も作らない**
  ——持っているのは軒数だけで、頑張りの度合いを語る材料が無い

## 作り直しのあとの焦点と読み上げ（#156）

`SearchAppInner` は payload ごとに作り直すので、押したボタンも消え、待つ間は disabled にも
なって焦点が body に落ちる。作り直されない `SearchApp` で受け持つ（[src/features/search/hooks/use-keyboard-focus-return.ts](../../src/features/search/hooks/use-keyboard-focus-return.ts)・[use-result-announcement.ts](../../src/features/search/hooks/use-result-announcement.ts)）。

- **キーボードで押したときだけ**、押したあとの 30 秒を毎フレーム見て、焦点が body に落ちていたら
  押せる状態の同じボタンへ戻す。Enter・Space の click は `detail` が 0 なのでマウスと見分けられる
- 結果を探し直す入力欄（`data-result-input` を付けた地名・店名の欄）で Enter を押したときは click が起きないので、キーで受けて
  その欄へ戻す。文言が変わるボタンには `data-focus-key` を付ける（「次の 3 軒」→「最初の 3 軒に戻る」）
- **名前ではなく押した要素で追う。** 待つ間は文言が変わる（「発券する」→「発券中…」）。名前で
  比べていたら、文言が変わった時点で「利用者が移した」と誤解して戻さなかった
- 外側の描画に頼らない。探し方の切り替えはサーバーを呼ばず、外側が描き直さないので、描画で
  確かめる形では戻らなかった
- 結果の読み上げは、作り直されない側の `role="status"` に `[data-announce]`（見出し・件数・
  「迷ったら」の題と何軒目か）の文を入れる。作り直す中に置くと、中身と一緒に生まれて読まれない
- 押したものがうまくいくと消えるもの（「もう一度試す」「このキーワードを外す」）なら、呼び出しが
  済んでも見つからない時点でページの見出しへ送る。**サーバーを呼ばずにその場で入れ替わる釦
  （「記録を全部消す」→「本当に全部消す」）は送らない**（次に押すものがそこに出ている）。
  焦点がアプリの外へ移ったら見守りをやめる。入れ替わった先へは `VisitedPanel` が自分で送る
  （キーボードのときだけ。確認の段では消さない方の「やめる」へ。#164）
- 選んだ時点で結果を差し替える選択欄（地図の都道府県）にも `data-result-input` を付ける。
  `change` には `detail` が無いので、直前の入力が `keydown` か `pointerdown` かで見分ける（#165）
- 読み上げは、結果ごと差し替えたとき（payloadVersion）は必ず読み、その場の書き換えは**前と文が変わったときだけ**読む。記録を消したとき
  のように差し替えずに書き換えた結果も読む一方、記録を押しただけ（見出しも件数も同じ）では読まない
- 「迷ったら」の 0 件・現在地が分からなかった案内は、画面の文と別に `StateNote` の `announce` で短い文を読ませる。ほかの探し方は見出しの件数（「判定した結果の 0 軒」）が読まれるので渡さない（0 軒を 2 度読む）
  （件数も題も出ないので、何も読まれなかった）
- **読み上げの領域は画面の文を複製する。** E2E で `getByText` を使うときは、行末まで一致させるか
  `main` の中に絞る（領域は `main` の外にあり、文は「。」で終わる）。途中経過の行は複製せず、
  見える行そのものを常に置いて `role="status"` にしてある（空のときは並びから外す）
- 会話の中のタブは `aria-controls` で結果の領域（`ModePanel`・`role="tabpanel"`）と結ぶ。
  箱を 1 つ足すので `.main` と同じ縦の並びと間隔にしてある

## 待つ間の見せ方（骨組み、#214）

結果を待つ間も、結果の場所を空けない。届いても配置を変えない（CLS を増やさない）。決めるのは
`src/features/search/hooks/use-result-state.ts`（`resultLook`）、出すのは `src/components/Pending.tsx`。見た目は `src/styles/global.css` の
`.pending-*`（別の CSS に分けると、トップで最初に読む CSS が 1 つ増えて FCP が 1.66 → 1.91 秒に遅れた）。

| 見え方     | いつ                                                                 | 見た目                                                  |
| ---------- | -------------------------------------------------------------------- | ------------------------------------------------------- |
| `hold`     | 同じ探し方で取り直して 300ms まで（次の 3 軒・発券・この範囲で発券） | 前の結果のまま。押せない（`inert`）                     |
| `dim`      | 同じ探し方で取り直して 300ms 以降                                    | 前の結果を薄く残す。押せない。「読み込み中」を 1 回読む |
| `reserve`  | 違う探し方へ移って 300ms まで                                        | その形の骨組みで場所だけ取り、見せない                  |
| `skeleton` | 違う探し方へ移って 300ms 以降                                        | 骨組み。押せない。「読み込み中」を 1 回読む             |

- **骨組みは、本物の部品に仮の店（`src/utils/skeleton.ts`）を渡して描き、文字を透明な帯にする。** 寸法を
  決め打ちすると、住所の行数などで本物と高さが違った（食券は 106〜131px）。光沢は付けない（動きは控えめ）
- 骨組み・前の結果から本物へは、薄くせず一度に入れ替える（薄く現れる動きは店の詳細だけ）
- 包む箱は `display: contents`。箱を作ると、親が並べるときの間隔が中から消えて高さが変わった（家系カメラで 36px）
- **結果が出ている間も同じ箱で包む。** 待ち始めたときだけ包むと中身が作り直され、食券が入ってくる動きを
  やり直して、前の結果が一度消えてから戻って見えた
- 同じ探し方の取り直しでは、**0 件の結果も残す**（`hold`・`dim`）。骨組みに替えると、また 0 件だったときに
  縮んで跳ねる。「行った店」へ移る間の骨組みは、先に分かっている記録の数（最大 8）だけ出す
- 地図（Leaflet）の先読みは、結果が出てから（つながる前の骨組みの間に読むと、最初の結果の通信と帯域を取り合う）
- **待つ間に前の結果を押せない。** 古い結果の店を選ばせない（#146 の「後から押したものが勝つ」）
- 件数の札は、件数が出る探し方では場所を先に取る（`AppHeader` の `reserve`。文字は置かず全角の空白で幅を取る）。
  届いた瞬間に札が差し込まれて約 20px ずれていた
- 接続前の画面も、画面 1 枚分の高さを取る（`src/features/search/styles/main-web.css`）。短いと下の規約のリンクが画面の中に出て、
  結果が届くと押し出されてずれに数えられた（トップの CLS 0.078）
- **Web はつながって最初の結果がそろうまでも、画面の本体を描く**（`src/features/search/utils/connecting.ts` の仮のホスト、
  `SearchAppInner` の `connecting`）。本体は押せない（`inert`）。見出し・探し方・券売機・「見つからないときは」・
  「家系とは」は最初から最終の位置に出て、結果の場所は骨組みが取る（見出しと札も本物と同じ長さの仮の文）。
  最初の結果がそろってから操作を許可する決まりは変えない。この間は最初の呼び出しを 1 件と数える
  （`data-pending-calls`。待つ仕組みが「済んだ」と取り違えない）。会話の中は、つながるのがすぐなので「読み込み中」のまま
- 「迷ったら」の 3 軒の並びは、そのページで出た一番高いものを保つ（`--tickets-min`）。営業時間の行の有無で
  食券が 106〜131px と違い、「次の 3 軒を見る」が入れ替わるたびに上下した
- 結果が届いて画面を自動で戻すのは、**3 軒が丸ごと画面より上にあるとき**（下の券売機で発券し直したとき）だけ。
  頭が少しはみ出ているだけで戻すと、「次の 3 軒を見る」を押すたびに画面が 160px 動いた
- 家系カメラの店の候補も同じ骨組み。家系マッチは札を出す舞台の大きさが決まっているので、今の「探しています」の紙のまま
- **音の仕組み（AudioContext）は、手が空いたときに先に作り、操作の中では再開だけする**（`src/lib/sound.ts`）。
  最初に作るときだけ約 150ms 止まる（CPU 4 倍遅くして）ので、払う操作の中で作ると最初の 1 回の反応が 208ms
  かかった。**再開（`unlock`）は操作の中で直接呼ぶ**——iPhone の Safari は、操作の中で再開しないと音を
  出させない（画面を描いた後に回すと鳴らなくなる）。鳴らす処理だけは `afterPaint` で画面を描いた後に回す
- 地図の「この範囲で発券」で取り直す間は、地図も押せない（古いピンを選ばせない）

## UI の選択をモデルに返す

UI で選んだ 1 軒は `app.updateModelContext()` でモデルに渡す。これが無いと、
地図で店を選んだ直後に「この店は？」と聞かれてもモデルは何も知らない。

- 文面は [src/features/search/utils/shop-brief.ts](../../src/features/search/utils/shop-brief.ts) に集約する。判定も味も推定なので、
  **但し書きごとモデルに渡す。** ここを削るとモデルが推定を事実として話す。
- 選択状態は外側の `SearchApp` が持つ。`SearchAppInner` は payload ごとに key で
  作り直されるので、内部に置くと検索のたびに消える。
- 選択を外すときは `{ content: [] }` を送る。空の content が「消す」の意味になる。
- `sendMessage` は即座にモデルを動かし、`updateModelContext` は次の発話まで待つ。
  詳細は context 側に置き、`sendMessage` には短い一文だけ流す。
