# ship-issue

issue を受け取り、**本番に出て確かめ終わるまで**を 1 本で通すスキル。
番号を複数渡されたら、渡された順に 1 件ずつ回す（並列にしない。前の変更の上に次を積むため）。

```
/ship-issue 41
/ship-issue 54 51 52
```

**このスキルで呼ばれたことが、マージしてよいという許可になる。** `/codex-review-loop` と
`/squash-and-merge` は単体では「マージはユーザーに聞く」が、ここではレビューが指摘ゼロで
CI が緑なら聞かずにマージしてよい。それ以外の判断（仕様の解釈が割れる・オーナーの操作が
要る）は止まって聞く。

## 1 件の流れ

### 1. 読む

```bash
gh issue view <番号>
gh issue view <番号> --comments
```

- **本文が仕様の正本。** 全文とコメントを読む。決まったこと（「残さない」など）がコメントに足されていることがある
- 依頼の文に追加の条件があれば、本文より優先する（例:「スクリーンショットは issue のコメントに残す」）
- 依存関係で止められていないか見る（`blocked by` が開いていれば、先にそちらを片付けるか聞く）
- AGENTS.md と、その参照先 docs/development.md のうち、触る領域の節を読み直す

### 2. オーナーの操作が要るかを先に洗い出す

**作り始める前に**、こちらでできないものを分ける。後から気付くと、待ちが 2 回になる。

| こちらではできない | 例                                                                                |
| ------------------ | --------------------------------------------------------------------------------- |
| 外部のコンソール   | Google Cloud の OAuth 設定・Cloudflare のダッシュボード（機能の有効化、トークン） |
| 実機の確認         | Claude Desktop・ChatGPT の画面、スクリーンショット                                |
| 決めること         | 旧い URL を残すか、など                                                           |

あれば、**番号付きの手順と所要時間**を 1 回にまとめて先に渡し、こちらで進められる部分は並行して進める。
新しい Cloudflare の binding（Analytics Engine など）は、**ダッシュボードで有効にしないとデプロイが落ちる**ことがある。マージ前に確かめる。

### 3. 作る

```bash
git checkout main && git pull && git checkout -b <短い英語のブランチ名>
```

- 不具合なら、**直す前に再現して数字を取る。** 回帰テストは直す前に戻して落ちることを確かめる
- 直す場所は呼び出し元を全部見てから決める（同じ関数を通る別の経路を残さない）
- 条件の裏側（匿名／サインイン済み、1 件／配列、UI 発／モデル発）を両方確かめる

### 4. 検証一式

AGENTS.md の「コマンド」にあるものを全部。結果は最後の行まで読む（oxlint は警告でも 0 を返したことがある）。

```bash
npm run format && npm run lint && npm run typecheck && npm run knip && npm test
npm run e2e        # UI・地図・会員機能に触れたとき
```

UI を変えたら `npm run build:ui`。**3031 と 8080 は止めない**（ユーザーが見ている）。

### 5. PR

- 本文: 目的・やったこと・やらないこと・確かめたこと（数字）
- 締め: マージで閉じてよいなら `Closes #<番号>`。**本番で確かめないと閉じられないもの**（計測・ドメイン・外部連携）は `Refs #<番号>` にして、7 で自分で閉じる
- 出したら `@codex review` を依頼する

### 6. レビューを指摘ゼロまで回し、マージする

- `/codex-review-loop` の手順で回す（待ちは `scripts/wait-codex-review.sh` を背景で）
- 指摘ゼロになったら `/squash-and-merge` の手順で、まとめて・CI の緑を待って・マージして・デプロイを見届ける
- **squash はレビューが済んでから。** squash したコミットは Codex がレビューしていないので、その後に依頼すると 1 巡増える
- 同じ指摘が 3 巡しても収束しなければ止めて聞く

### 7. 本番で確かめて、証拠を残す

- `curl https://iekeiramen.com/health` が 200
- その issue の完了条件を、**本番で 1 つずつ**確かめる（例: tool を呼んで数えられたか、新しいドメインで 401 が正しい場所を指すか）
- issue にコメントで残す: 確かめた項目と結果（表）、オーナーが確かめたもの、満たせなかった条件とその理由
- `Refs` で出したものは、ここで `gh issue close` する

### 8. 次へ

次の番号があれば 1 へ。オーナーの操作待ちで止まった issue は飛ばさず、待っていることを報告して止まる。

## 報告

全部終わったら（または止まったら）、1 回だけ:

```
| issue | PR | 巡 | 本番 | 状態 |
| --- | --- | --- | --- | --- |
| #58 | #64 | 2 | 確認済み | 閉じた |
| #40 | #65 | 3 | 確認済み | 閉じた |
| #42 | #67 | 1 | — | オーナーの実機確認待ち |
```

そのあと、オーナーにお願いすることを番号付きで（所要時間つき）。

## やらないこと

- **秘密の値を画面に出さない。** `.dev.vars` は名前と長さだけ見る（値を含む行を cat / awk しない）。トークンをチャットや issue に貼らせない
- 検証が通る前に PR を出さない・返信しない
- 本番を確かめずに「完了」と報告しない
- issue を `gh issue create` で直接作らない（`/create-issue` を使う）
