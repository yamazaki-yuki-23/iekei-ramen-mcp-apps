# codex-review-loop

PR を出したあとの「レビュー待ち → 指摘対応 → 返信 → 再依頼」を、**指摘がゼロになるまで自分で回す**スキル。

ユーザーに「レビューが来ています」と知らせてもらうのを待たない。待ちの合図を人に出させるのは無駄。

## review-response との使い分け

|                   | 使う場面                                                                          |
| ----------------- | --------------------------------------------------------------------------------- |
| **このスキル**    | PR を出した直後から、**指摘ゼロになるまでの全体**を回す。レビューの到着待ちを含む |
| `review-response` | 既に手元にある特定のレビューコメント 1 件〜数件に対応する（ループしない）         |

このスキルの中で 1 件ずつ処理する部分は `review-response` と同じ考え方でよい。

## 引数

```
/codex-review-loop [PR番号]
```

省略時は現在のブランチの PR を `gh pr view --json number -q .number` で引く。

---

## ループ

```
1. レビューの到着を待つ（背景ジョブ）
2. 未返信の指摘を抽出する
3. 指摘ゼロ？ → はい: 終了（マージ可否はユーザーに聞く）
                 いいえ: 4 へ
4. 再現する
5. 直す
6. 回帰テストを足し、直す前に戻すと落ちることを確認する
7. プロジェクトの検証一式を通す
8. コミット・push
9. 各指摘に根拠つきで返信する
10. @codex review で再依頼 → 1 へ
```

---

## 1〜2. レビューの到着を待ち、未返信の指摘を出す

**待ち方はその場で書かない。** [scripts/wait-codex-review.sh](../../../scripts/wait-codex-review.sh) を
`run_in_background: true` で呼ぶ（Bash の前景実行は 600 秒で切れる）。PR 番号は省略すると
今のブランチの PR。

```bash
scripts/wait-codex-review.sh        # または PR 番号を付ける
```

| 終了コード | 意味                                                         | 次                                           |
| ---------- | ------------------------------------------------------------ | -------------------------------------------- |
| 0          | 指摘なし（総評の 1 行と「未返信の指摘: なし」が出る）        | 3 へ                                         |
| 3          | 未返信の指摘あり（`id=… path:line` と本文が出る）            | 4 へ                                         |
| 4          | 40 分待っても届かない（`CODEX_WAIT_TIMEOUT` 秒で変えられる） | 依頼のコメントが付いているか見て、依頼し直す |

スクリプトが見ているもの（**どれも一度ずつ踏んで、待ち違えた**）:

- **PR の先頭のコミット**（手元の HEAD ではない）。push し忘れると古いコミットを待つので、食い違えば注意を出す
- **いちばん新しい `@codex review` より後の結果だけ**を見る。コードを変えずに反論して依頼し直すと head は同じなので、前の巡の結果が「届いた」に見える（総評は書き換えて使い回されるので `updated_at` で比べる）
- 届いた合図は 2 通り。どちらも SHA を持つ。どちらか 1 つで「届いた」とする
  - reviews API の `commit_id` が先頭の SHA と一致する（**指摘ありの回はこれでしか来ない**。総評だけ見ていると永久に待つ）
  - 総評コメントで、7 桁の SHA と `Completed` が**同じ行**にある（`Running` の行にも SHA が出るので、SHA だけで待つとレビューの途中で早合点する。10 桁で探して 1 時間待ち続けたこともある）
- **依頼への 👍 は見ない。** SHA を持たないので、前の巡の 👍 と今の head を結び付けられない。コミットの日時で比べても、溜めていたコミットや作り直しは依頼より古い日時のまま push される（レビューで 2 度指摘された）。指摘なしの回も総評に Completed の行が出るので、それを待てば足りる
- 未返信の判定は、全ページをまとめてから突き合わせる。`--paginate` に `--jq` を付けるとページごとに評価され、返信が次のページにあると未返信に見える（コメントが 30 件を超える巡で起きる）

**squash した直後のコミットは、Codex がレビューしていない。** squash 後に待つと時間切れになる
（正しい振る舞い）。squash はレビューが済んでからにする。

CI も同時に見ておくと、落ちていたときに 1 往復減る。

```bash
gh pr checks
```

## 3. 指摘ゼロなら

ループを抜ける。**勝手にマージしない。** squash・マージ・ブランチ削除はユーザーに確認する。
指摘があった回は、何を直したかを一覧でユーザーに報告する。

## 4. 再現する

**読んで納得しただけで直さない。必ず数字で再現する。**

指摘は正しいこともあれば的外れなこともある。再現できないものは「対応不要」と判断してよく、
そのときは**なぜそう判断したかを返信に書く**（黙って閉じない）。

再現の例:

- レイアウトの溢れ → Playwright で `scrollWidth - clientWidth` を幅ごとに測る
- 見た目の状態 → `getComputedStyle(el)` を読む
- 競合状態 → 順序を固定した小さな再現スクリプト

再現できた数字は、あとで返信にそのまま載せる。

## 5. 直す

指摘は 1 件ずつ順に処理する（修正が積み重なるため並列にしない）。

**原因を 1 つ見つけて満足しない。** 同じ症状に経路が 2 本あることがある。
このループで実際にあった例: 焦点リングが消える問題は「CSS の順番」と「hover の指定の方が強い」の
**両方**を直さないと塞がらなかった。順番だけ直してテストが通り、危うく見逃すところだった。

## 6. 回帰テストを足し、**効くことを確かめる**

**足したテストが本当に落ちるか、直す前の状態に戻して確認する。** ここを飛ばすと、
何も見張っていないテストが増えるだけになる。

```bash
cp <対象ファイル> /tmp/keep && <直す前の状態に戻す>
<そのテストだけ実行>        # ← 落ちること。落ちた値も見る
cp /tmp/keep <対象ファイル> && rm /tmp/keep
```

原因が 2 つあったなら、**片方ずつ戻して 2 回**確かめる。落ちたときの値が別なら、
それぞれ別の経路を見張れている。

### ここで必ず踏む罠

**古いサーバーが残っていると、古いビルドを検証してしまう。**
テストが「通った」のに実は何も変わっていない、という偽の合格が起きる。
確認前にポートを見て、残っていれば止める。

```bash
for p in <プロジェクトのポート>; do
  lsof -ti tcp:$p -sTCP:LISTEN | while read pid; do
    echo "port $p -> $pid $(ps -o command= -p $pid | cut -c1-60)"
  done
done
```

自分で起動したサーバーだけ止める。ユーザーが見ているプレビューは勝手に落とさない。

## 7. 検証一式を通す

**プロジェクトの CLAUDE.md にコマンドが書いてある。** それを読んでから実行する。
典型的には lint / format / typecheck / 未使用検出 / ユニット / E2E。

返信する前に全部通す。落ちたまま「直しました」と返信しない。

## 8. コミット・push

コミットメッセージには**なぜそうしたか**を書く。指摘の引用ではなく、原因と対処。
プロジェクトの規約（言語・署名行）に従う。

## 9. 返信する

**根拠を載せる。「修正しました」だけの返信はレビューとして成立しない。**

入れるもの:

1. 指摘が正しかったか（正しければ再現した数字）
2. 何をどう直したか。**なぜその直し方なのか**
3. 直す前 / 直した後の比較表があれば強い
4. 足した回帰テストと、それが直す前に落ちることを確認した旨
5. コミット URL

返信先のエンドポイントは **PR 番号が要る**。`pulls/comments/<id>/replies` は 404 になる。

```bash
gh api "repos/$REPO/pulls/$PR/comments/<comment_id>/replies" \
  --method POST --field body="$(cat <<'EOF'
<本文>
EOF
)" --jq '.html_url'
```

対応不要と判断したときも同じ形式で、**なぜ不要か**を書いて返信する。

## 10. 再依頼

```bash
gh pr comment "$PR" --body "@codex review"
```

push してから依頼する。順番を逆にすると古いコミットをレビューされる。
依頼したら 1 に戻る。

---

## 終わり方

- 指摘ゼロになったらループを抜け、**各ラウンドで何を直したかを表でユーザーに報告する**
- マージするかはユーザーが決める。squash・マージ・ブランチ削除は勝手にやらない
- 同じ指摘が 3 巡しても収束しないときは、ループを止めてユーザーに相談する

## 報告の形

```
| 巡 | コミット | 指摘 | 対応 |
| --- | --- | --- | --- |
| 1 | 3557506 | なし | — |
| 2 | 1d10a8f | P2: 375px でタブが溝からはみ出す | 折り返し対応＋回帰テスト |
| 3 | 856c9d3 | P2: 選択中のカードで焦点リングが消える | 2 か所修正＋回帰テスト |
| 4 | 856c9d3 | なし | — |
```

## やらないこと

- **ユーザーからの合図を待たない。** 自分でポーリングする
- **再現せずに直さない。** 指摘が的外れなこともある
- **効くか確かめていない回帰テストを足さない**
- **検証が通る前に返信しない**
- **勝手にマージしない**
